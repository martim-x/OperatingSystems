## Реализация задержки: активное ожидание, а не `usleep`

По предварительному замеру, описанному в рабочих записях, если задержку делать через `usleep(50 мс)`, прогон длится 50.5 с,
а процессорного времени тратится 0.02–0.09 с. Нагрузка практически нулевая, планировщику
нечего делить, и расхождения между потомками не возникает ни при каких nice, включая один CPU.
Этот предварительный замер **не входит в итоговый набор доказательств** (кадров и логов от него
в `скрины/` и `выводы/` нет) и приведён только как обоснование выбора реализации.

Поэтому «задержка 50 мс» реализована **активным ожиданием** по `CLOCK_MONOTONIC`: процесс всё
это время остаётся готовым к выполнению, и приоритеты начинают работать.

## Серии замеров (2026-11-15, Arch Linux ARM, 6 CPU, gcc 16.1.1)

По сохранённым логам все прогоны — 1 млн итераций, задержка 50 мс каждые 1000 итераций, задержка активная. Указание 50 мс расходится с PDF задания (200 мс) и зависит от неподтверждённой письменно поправки.
В сохранённых Linux-логах обе программы в каждой серии сообщают о штатном завершении после
1 000 000 итераций. Проверяющий скрипт завершился с кодом 0; это не подтверждает содержание
каждого кадра, и ниже перечислены случаи, где подпись кадра шире фактического доказательства.
Периодический вывод идёт с шагом 1000 и обычно заканчивается строкой 999 000 перед финальной
строкой 1 000 000; значение последней периодической строки не является числом итераций на
момент завершения.

| Серия | P1/P2/P3 | CPU | PID участников | Первый финиш | Дельта | Длительность | Кадры |
|---|---|---|---|---|---|---|---|
| b1 | 0 / 0 / 0 | все (маска 111111) | 202011, 202012 | t=49.967 с | 0.001 с | 51.2 с | 6 |
| b2 | 0 / 19 / −20 | все | 205073, 205074 | t=49.992 с | 0.017 с | 51.3 с | 6 |
| b3 | 1 / 19 / −20 | CPU 0 | 208152, 208153 | t=50.011 с | 49.725 с | 100.5 с | 7 |
| c1 | 0 / 0 / 0 | все | TID 212942, 212943 | t=49.972 с | 0.000 с | 51.4 с | 6 |
| c2 | 0 / 19 / −20 | все | TID 216002, 216003 | t=49.971 с | 0.000 с | 51.1 с | 6 |
| c3 | 1 / 19 / −20 | CPU 0 | TID 219083, 219084 | t=49.973 с | 49.776 с | 100.7 с | 7 |

Колонка «Первый финиш» — время первого завершения по `CLOCK_MONOTONIC` из консольного лога,
«Дельта» — интервал между завершениями двух участников из сводки серии.

Смысл строк:

- **b1, b2, c1, c2 — одно окно финиша.** Участники завершаются с разницей 0.000–0.017 с, то есть
  внутри одного опроса `pgrep` (100 мс). Отдельный кадр «второй ещё работает» в этих прогонах
  не получен: кадр `g_finish` сообщает, что второй на момент фиксации уже завершён. Кадр
  `e_first` не является снимком живого второго в момент первого завершения.
- **Linux b3, c3 — разные моменты.** При маске на один CPU (000001) первым завершается
  участник с `nice −20` (t≈50.0 с), второй живёт ещё ~49.7 с и завершается на t≈99.7 с.
  В Linux-сериях `f_second` показывает продолжение вывода второго участника после первого финиша.
  Это не распространяется на Windows b3/c3: там лог сообщает `кадров в буфере: 0` для b3
  и 30 для c3, но кадр c3 — кольцевой кадр без самого события/списка оставшихся TID.
- **b3/c3: сколько успел низкоприоритетный.** На момент первого финиша в логе у `nice 19`
  было 4 000–5 000 итераций (`05b_b3_консоль.txt`, `05c_c3_консоль.txt`), т.е. ~0.4–0.5 % работы;
  после ухода высокоприоритетного он доходит до 1 000 000 за вторые ~50 с. Поле
  «последняя итерация» в `*_summary.txt` показывает конечное значение (999 000 у обоих) и
  снимком на момент первого финиша не является.

## Выводы

- **При свободных процессорах приоритет не влияет.** В b1/b2/c1/c2 каждый участник попадает
  на свой CPU, конкуренции нет; разница в 0.000–0.017 с — это разница во времени старта и
  момент выхода из активного ожидания, а не вытеснение по приоритету.
- **На одном CPU приоритет решает.** В b3/c3 `nice −20` проходит все 1 000 000 итераций за
  ~50 с, а `nice 19` к этому моменту успевает 4 000–5 000 итераций (≈0.4–0.5 %). Оба претендуют
  на одно ядро, CFS делит время по весам (nice −20 → вес 88761, nice 19 → вес 15), и
  низкоприоритетный получает процессор только когда высокоприоритетный уступает его сам.
  Второй участник после этого дорабатывает ещё ~50 с — итог тот же миллион итераций, но вдвое
  дольше по стенному времени.
- **Потоки ведут себя как процессы** (c3 против b3): внутри одного процесса потоки конкурируют
  за тот же CPU по тем же правилам nice; разница лишь в том, что поток не несёт собственного
  адресного пространства и переключение между потоками дешевле. Для 05c `clock()` в логе —
  это CPU-время всего процесса (≈98 с при двух потоках), а не время отдельного потока;
  стенное время считается по `CLOCK_MONOTONIC`.

## Ответы на вопросы для самоконтроля

Вопросы переписаны из конца `lab5/lab5.docx`; ответы составлены по лекции 6 «Диспетчеризация
и планирование» и уточнены по материалам лабораторной. Числовые шкалы и системные вызовы
различаются между Linux и Windows — платформу указываю в каждом ответе, где это важно.

1. **Поясните понятия планирование и диспетчеризация?** Планирование выбирает следующий
   готовый к выполнению процесс/поток согласно принятой политике. Диспетчеризация передаёт
   ему CPU: сохраняет контекст прежнего исполнителя, загружает контекст выбранного и
   продолжает его выполнение. Планировщик принимает решение, диспетчер выполняет переключение.
2. **Опишите процесс диспетчеризации?** При событии перепланирования управление переходит в
   ядро; ОС сохраняет регистры и состояние текущего потока, выбирает готовый поток, восстанавливает
   его контекст и передаёт ему CPU. Переключение контекста требует времени и снижает долю
   полезной работы, если происходит слишком часто.
3. **Что такое планировщик? Какие бывают планировщики? Опишите каждый из них.** Планировщик
   распределяет работу и выбирает объект для выполнения. Долгосрочный допускает задания в
   систему; среднесрочный временно выгружает и возвращает процессы в память; краткосрочный
   выбирает готовый поток для CPU; планировщик ввода-вывода выбирает запрос для устройства.
4. **Какой из планировщиков определяет степень мультизадачности ОС?** Долгосрочный: допуская
   задания, он влияет на число одновременно активных процессов.
5. **Какие виды алгоритмов планирования вы знаете?** Есть вытесняющие и невытесняющие
   алгоритмы. Примеры политик выбора: FCFS, SJF/SJN, SRT, Round Robin, приоритетное планирование,
   многоуровневые очереди (MLFQ), lottery и fair-share.
6. **Перечислите общие и специфичные задачи планирования.** Общие — справедливое распределение
   CPU, соблюдение политики и баланс ресурсов. Пакетным системам важны пропускная способность
   и оборотное время; интерактивным — малое время отклика; системам реального времени — сроки
   и предсказуемость.
7. **Поясните понятие «циклическое планирование».** Round Robin выдаёт готовым потокам кванты
   по очереди. Не завершивший работу поток после кванта помещается в конец очереди. Малый квант
   обычно улучшает отклик, но увеличивает расходы на переключения.
8. **Поясните понятие «приоритетное планирование».** Планировщик выбирает наиболее
   приоритетный готовый поток; при вытесняющей политике более приоритетный может прервать
   текущий. Низкоприоритетные задачи могут голодать; старение помогает смягчить проблему.
9. **Поясните понятие «приоритет процесса».** Это параметр, влияющий на предпочтительность
   вычислительной работы, а не фиксированная доля CPU. В Windows класс процесса участвует в
   формировании базовых приоритетов его потоков; в Linux `nice` влияет на вес планируемой
   задачи. Планировщик фактически выбирает потоки.
10. **Что такое базовый приоритет потока, как он вычисляется и диапазон его изменения?** В
    Windows он формируется сочетанием класса процесса и относительного приоритета потока.
    Для `Normal` база 8; в примерах лаборатории `Lowest` даёт 6, `Highest` — 10. Обычный
    диапазон — 1–31; уровень 0 зарезервирован системному потоку обнуления страниц. Динамический
    приоритет может меняться отдельно. Это шкала Windows, не шкала Linux `nice`.
11. **Поясните принцип использования значения nice – процесса, диапазон его изменения.** В
    Linux `nice` находится в диапазоне −20…+19: чем меньше значение, тем выше вес задачи среди
    конкурирующих за CPU; значение по умолчанию — 0. Это не квота и не абсолютная скорость.
    Для повышения приоритета (уменьшения nice) нужны соответствующие права.
12. **Поясните понятие «кооперативное планирование».** Это невытесняющее планирование:
    поток исполняется до завершения, блокировки или добровольной уступки CPU. Если он не
    уступает управление, остальные задачи могут ждать.
13. **Поясните понятие «родственное планирование».** Processor affinity стремится оставить
    поток на прежнем CPU ради локальности кэша и меньшего числа миграций. Без жёсткой маски это
    предпочтение планировщика, а не гарантия постоянного CPU.
14. **Что такое маска родственности? Как задать?** Это битовое множество разрешённых CPU:
    единичный бит разрешает соответствующий процессор. В Windows применяют `Get/SetProcessAffinityMask`
    и `SetThreadAffinityMask`; в Linux — `sched_getaffinity`/`sched_setaffinity` и
    `pthread_*affinity_np`. Маска должна включать CPU, доступные процессу.
15. **Что такое перепланировка? Когда наступает момент перепланировки?** Это повторный выбор
    потока для CPU, когда меняется набор готовых задач или текущий исполнитель не может/не должен
    продолжать: истёк квант, поток блокируется или завершается, пробудилась ожидающая задача либо
    стал готов более приоритетный поток.

## Как снимались кадры

Драйвер `~/lab5_sync` живёт внутри окна Konsole на машине: берёт команды из `queue/`, печатает
приглашение и вывод, после каждой команды снимает экран `spectacle`. Скрипт серии
(`linux/tools/run_05b_series.sh`, `run_05c_series.sh` через `series_lib.sh`) снимает этапы:

| Этап | Что показывает кадр |
|---|---|
| `a_params` | баннер серии с `P1/P2/P3` и команда запуска — до начала нагрузки |
| `b_early` | первые блоки вывода (итерации около 0) |
| `c_ps` | `ps -L`/`/proc`: PID, TID, nice, CPU, маска |
| `d_mid` | середина прогона |
| `e_first` | кадр, связанный с первым финишем; при близких финишах может быть снят уже после обоих |
| `f_second` | только если второй на этот момент жив (b3, c3) |
| `g_finish` | финал: коды возврата и строка драйвера о том, завершился ли второй |

Панель KDE срезается `tools/crop_panel.py`. Для каждого кадра в `*_frames.tsv` пишутся метки
времени по `/proc/uptime` (до и после съёмки).

## Требования к правам (Linux)

`nice` в минус требует `CAP_SYS_NICE`: без него `setpriority` даёт `Permission denied`,
а `ulimit -e = 0`. Решение — файловые capability на бинарники:

```bash
sudo setcap cap_sys_nice+ep ~/OS5/Lab-05b
sudo setcap cap_sys_nice+ep ~/OS5/Lab-05c
```

Важно: `setcap` разбирает аргументы **парами** «caps файл», поэтому `setcap cap_sys_nice+ep f1 f2`
второй файл принимает за спецификацию capability и падает с `Invalid argument`. Пересборка
(`build.sh`) пересоздаёт файлы и **снимает** capabilities — после каждой сборки ставить заново.

```bash
python3 tools/check_evidence.py \
  --shots "linux/скрины/уровень_4-5" \
  --logs "linux/выводы/уровень_4-5" \
  --ocr "linux/выводы/уровень_4-5/ocr_кадры.txt"
```

полностью доказана. Подробный список недостатков и кадров для пересъёмки приведён в
